    CalDAV sync

    org-extensions-caldav

    Stability: experimental (org-extensions-stability)

    caldav keeps a calendar of a CalDAV server and org files in step, both ways, like Emacs's org-caldav: the calendar's events become headings of an org file, entries with a date become events, and what changes on one side is carried to the other by :Org caldav_sync. With todos, entries with a TODO keyword sync as the calendar's tasks. (To only see a calendar in the agenda, org-extensions-ics is simpler: it needs no account.)

    require("org").setup({
  agenda_files = { "~/org/calendar.org" },
  extensions = {
    caldav = {
      calendars = {
        {
          name = "Personal",
          url = "https://cloud.example.com/dav/calendars/me/personal/",
          user = "me",
          password = { "pass", "show", "cloud/caldav" },
          inbox = "~/org/calendar.org",
        },
      },
    },
  },
})

    Getting started

    1. Put the calendar in calendars as above, with the address your provider gives for CalDAV as url and your user and password (or a token; for Google see org-extensions-caldav-google).
    2. :checkhealth org says what is missing or misspelt.
    3. :Org caldav_discover lists the calendars of the account. Copy the url of the one you want into the calendar.
    4. For a first look, give it direction = "pull" and an inbox that is a new file: nothing is sent to the calendar or deleted there.
    5. :Org caldav_sync. Its message says what it did, such as caldav: Personal: 12 from the calendar (org-extensions-caldav-messages).
    6. Take direction out to sync both ways, and list the file in agenda_files to see the events in the agenda.

    To sync with a key, or every 15 minutes by itself:

    mappings = { global = { caldav_sync = "<leader>cs" } },
extensions = { caldav = { interval = 15, calendars = { ... } } },

    Calendars

    Each calendar takes:

    nameshown in messages and :checkhealth org (calendar1, ... when left out)
    urlthe address of the calendar itself (a collection, ending in /). :Org caldav_discover lists the calendars of an account with their addresses: set url to the address your provider gives for CalDAV, run it, and copy the one you want
    user, passwordthe account. password is a string, a function returning one, or a command (a list) whose first line of output is used, such as { "pass", "show", "dav" }, so the password need not be in your config. Where the provider has app passwords, use one
    tokeninstead of user and password: a bearer token, in the same three forms. A token function or command, and a password command, are called again when the server refuses what they gave
    auth"basic" (the default), "digest" or "any"
    headersextra request headers, { Name = "value" }
    inboxthe org file new events of the calendar are added to, at the top level; or { file = ..., headline = "Calendar" } to add them under that heading (made when missing). Its entries are sent too
    filesmore org files whose entries are sent to the calendar

    and may set direction, conflict, delete_local, delete_remote, todos, past_days, sync_on_open and sync_on_save for itself. A calendar needs an inbox or files; with files only, the calendar's new events are not added anywhere (the sync says how many). A file belongs to one calendar. List the files in agenda_files to see the events in the agenda.

    Entries and events

    An entry and an event belong together when the entry's ID property is the event's UID, as with org-caldav (files synced with it carry over). An event of the calendar is written as:

    * Design review
:PROPERTIES:
:ID:       6f1e9c0a-41d7-4a57-9d0e-2f6c1b7a9e11
:LOCATION: Room 4
:END:
<2026-11-12 Thu 15:00-16:00>
Bring the mockups
    titlethe heading; its keyword, priority and tags are yours
    timethe timestamp line below the drawers. In an entry you wrote, also the first active timestamp of the heading or its text, else SCHEDULED or DEADLINE (in an entry without a TODO keyword only, as in org-export-icalendar). All-day events, several days (<a>--<b>) and end times are kept. Of several timestamp lines you wrote, the first is the event's
    locationthe LOCATION property
    descriptionthe text below the timestamp line: all of it is sent, so keep private notes out of an entry of a shared calendar. When the calendar changes the text of an entry whose time is a timestamp in that text, and the new text doesn't hold it, the timestamp moves to a line of its own above it

    An entry of the calendar's files that has an active timestamp, and no ID the calendar knows, is sent as a new event and gets an ID. Entries without a date are never sent, nor are new COMMENT entries, inline tasks and entries in a subtree tagged ARCHIVE (one that is synced already stays synced when it gets the tag or the keyword). The keyword, the priority, the tags, the drawers and the subheadings stay in org; attendees, alarms and everything else an event holds stay in the calendar: a change is sent by replacing only the changed properties of the event the server has.

    Timestamps are in the system's zone, or in timezone. A changed time is sent in the zone the event has. A new event's time is sent in UTC; one that repeats is sent in your zone when its name is known (timezone, $TZ or what /etc/localtime links to), so that it keeps its hour across clock changes. On Windows the name is only known from timezone: set it there, or such an event drifts an hour at a clock change in other calendar programs (:checkhealth org says when the name isn't known).

    The sync

    :Org caldav_sync asks the server what changed since the last sync and compares each entry with its event, a field at a time:

    • what changed in the calendar is written into the entry, what changed in the entry is sent; changes of different fields are both kept;
    • when the same field changed on both sides the org one is kept, as org-caldav does (conflict = "remote": the calendar's), and the message says so;
    • new events are added to the inbox, new entries are sent;
    • for an event deleted in the calendar, delete_local says what happens to its entry: "ask" (the default), "always" delete it, or "never". An entry that is kept is asked about again at the next sync, and is sent again as an event once you change it. An entry with subheadings is never deleted;
    • for an entry deleted in org (or archived to another file, or moved to a file that is not the calendar's), delete_remote says what happens to its event, in the same three ways;
    • on either side, when everything a calendar had (two entries or more) would be deleted at once, it asks even with "always": that looks like a lost file or another calendar;
    • an event deleted on one side and changed on the other comes back (except an entry whose dates follow a rule of the calendar, below: delete_local decides).

    Events that ended more than past_days days ago are not picked up, on either side; one that is synced stays synced as it grows older. With todos, open tasks are always picked up, and done ones unless they were closed that long ago. The org files a sync changed are saved (save).

    direction = "pull" only brings the calendar's changes to org: nothing is sent or deleted there, the calendar's value wins a conflict, and an entry you delete in org is added again by the next sync (delete_remote is not asked). direction = "push" only sends org's: the entries are not changed, new events are not added, org's value wins, and an event deleted in the calendar is sent again (delete_local is not asked).

    What was synced is kept in state_dir, one file per calendar. Without it (a new machine) entries and events are matched by ID again: nothing is duplicated; a field one side lacks is filled from the other, and where both have different values conflict decides. A change that could not be sent is sent at the next sync.

    With interval, a sync also runs every that many minutes. It asks no questions (deletions that need an answer wait for :Org caldav_sync) and reports only changes and failures.

    org-extensions-caldav-triggers

    Two more syncs that ask nothing and report the same way, off by default:

    sync_on_opensyncs a calendar when one of its files is shown in a window (opened, or gone back to), unless the calendar was synced less than open_interval minutes ago (5). It brings the calendar's changes, so it does nothing for a calendar with direction = "push".
    sync_on_savesyncs a calendar a moment after one of its files is saved: by :w, and by org's own saves (capture, refile, agenda edits). Saves close together, such as :wa, make one sync, and a save while a sync runs is synced when it ends. It sends org's changes, so it does nothing for a calendar with direction = "pull". The sync's own saves start no other.

    Either syncs the whole calendar of the file, which sends and fetches only what changed. Expect the buffer to change after a save: a new entry with a date gets its ID property (the sync saves the file again, with save), and the calendar's changes come in. Both can be set per calendar:

    extensions = { caldav = { sync_on_open = true, calendars = {
  { name = "Work", url = "...", inbox = "~/org/work.org",
    sync_on_save = true },
} } },

    Repeating events

    A rule a repeater can say is written as one (FREQ=WEEKLY is +1w), and a repeater of yours is sent as a rule. An event every week on several days (its first day among them) is written as one timestamp a day, each with +1w. Any other rule (a count or an end date, exceptions, moved or cancelled instances, every other week on several days, "the second Tuesday", an event that runs past midnight) is written as the timestamps of its occurrences, from past_days ago (30 days when it is false) to recurrence_days ahead, brought up to date by each sync. The dates of those two kinds follow the calendar: change them there (a change in org is put back). Their title, location and description sync both ways as usual.

    Tasks

    With todos = true, entries with a TODO keyword sync as tasks (VTODO), with or without a date, instead of as events: SCHEDULED is the task's start and DEADLINE its due date, a done keyword completes it (CLOSED is when), a done keyword starting with CANCEL cancels it, and the priority cookie is its priority (1-4 the highest, 5-8 the default, 9 the lowest, as in org-caldav). A task completed in the calendar gets the file's first done keyword that doesn't start with CANCEL, a cancelled one the first that does (else the first done keyword), a reopened one the first TODO keyword. The calendar must be one that holds tasks; :Org caldav_discover shows what each holds. Whether an entry is an event or a task is settled when it is first synced. todos is off by default, so a calendar that holds only tasks (a Radicale task list, say) needs todos = true; without it nothing syncs, and :Org caldav_sync says how many tasks it left out. Tasks synced while todos was on keep syncing after it is turned off.

    Servers

    Any server that speaks CalDAV (RFC 4791) and takes a password (basic or digest) or a bearer token. Radicale and Google Calendar are the ones it was tried with; reports about others are welcome.

    org-extensions-caldav-google

    Google Calendar

    Google takes OAuth tokens only, so it needs token set to a command that prints one, such as Google's oauth2l:

    {
  name = "Google",
  url = "https://apidata.googleusercontent.com/caldav/v2/"
    .. "you@gmail.com" .. "/events/",
  token = {
    "oauth2l", "fetch", "--type", "oauth", "--refresh",
    "--credentials", vim.fn.expand("~/client_secret.json"),
    "--scope", "https://www.googleapis.com/auth/calendar",
  },
  inbox = "~/org/google.org",
}

    The address holds the calendar's ID: your address for the main calendar, else the "Calendar ID" under "Integrate calendar" in the calendar's settings. :Org caldav_discover also works, from https://apidata.googleusercontent.com/caldav/v2/CALENDAR_ID/user.

    For the token, once, in the Google Cloud console:

    1. make a project and enable the "CalDAV API" in it;
    2. under Google Auth Platform, make an OAuth client ID of the type "Desktop app" and download it as client_secret.json;
    3. under Audience > Test users, add your own address. Without it the sign-in stops at "Access blocked ... Error 403: access_denied";
    4. run the oauth2l command of the example in a terminal (it comes from brew install oauth2l, or its binaries): it opens the browser to sign in, then prints the token. It keeps it in ~/.oauth2l and renews it.

    Google's CalDAV holds no tasks (leave todos off), and Google Tasks are not on CalDAV at all. A new repeating entry is sent in your time zone, or in UTC when the zone has no clock changes.

    Actions

    caldav_syncsync every calendar now; :Org caldav_sync NAME syncs one (names complete)
    caldav_discoverlist the calendars of the account of each configured calendar, with their addresses and what they hold, in a window (q closes it); :Org caldav_discover NAME for one, :Org caldav_discover URL for another address, asked with the credentials of the first calendar on that server

    Neither has a default key; map them in mappings or run them with :Org.

    org-extensions-caldav-messages

    Messages

    A sync ends with one line a calendar:

    caldav: NAME: up to datenothing changed on either side
    ... N from the calendarentries added or changed in org
    ... N to the calendarevents added or changed in the calendar

    ... N deleted here, N deleted in the calendar

    When the sync could not run, the line says why instead:

    401: the server refused the user, password or tokenWrong credentials. Run a password or token command in a terminal to see what it prints; for Google see org-extensions-caldav-google.
    404: not found (check the calendar's url)url is not a calendar: :Org caldav_discover lists them.
    403: the server does not allow itUsually a calendar you may only read.
    it has no inbox ..., FILE not found, curl not foundWhat the calendar's settings lack; :checkhealth org says the same.

    Lines below it name the entries that need a look:

    "Title": not sent: ...The server refused it, and this is its reason. 412: it changed on the server settles at the next sync; 403 can be a task sent to a calendar that holds only events. The change stays in org and is sent again by every sync until it is taken.
    "Title" has no timestamp: not sentAn entry needs a date to be an event.
    "Title": summary changed here and in the calendar; kept the org oneThe same field changed on both sides; conflict decided.
    "Title": its dates follow a rule of the calendar; change them thereA repeating event a repeater can't say: a date changed in org was put back.
    "Title" is kept: it has subheadingsIts event was deleted in the calendar; delete the entry yourself.
    N deletion(s) wait for :Org caldav_sync to ask about themA sync in the background asks no questions.
      N new in the calendar, not added: it has no inbox
    two entries have the ID ...; only the first is syncedA copied entry: take the ID out of the copy.

    A sync in the background shows only the first line, with the number of notes; :Org caldav_sync shows them all.

    To start over with a calendar, delete its file in state_dir. The next sync matches entries and events by ID again and duplicates nothing.

    Options

    calendarsthe calendars (above) ({})
    direction"twoway", "pull" or "push" ("twoway")
    conflict"local" (org wins) or "remote" ("local")
    delete_local"ask", "always" or "never" ("ask")
    delete_remote"ask", "always" or "never" ("ask")
    todossync entries with a TODO keyword as tasks (false)
    past_daysdays back events are picked up; false: all (30)
    recurrence_daysdays ahead the occurrences of a rule are listed (90)
    intervalminutes between syncs in the background; 0: none (0)
    sync_on_opensync a calendar when one of its files is shown (org-extensions-caldav-triggers) (false)
    open_intervalminutes after a calendar's last sync before sync_on_open syncs it again (5)
    sync_on_savesync a calendar after one of its files is saved (false)
    savesave the org files a sync changed (true)
    timezoneIANA zone of the timestamps (nil: the system's)
    tz_aliasesextra TZID -> IANA zone names ({})
    state_dirwhere the state of each calendar's last sync is kept (stdpath("data") .. "/org/caldav")
    curlthe program requests are sent with and extra arguments, e.g. { "curl", "--netrc" } ({ "curl" })
    timeoutseconds before a request is given up (60)

    Requests are sent with curl, which gets the address, the headers and the credentials on its standard input, not as arguments, so they don't show in the process list. :checkhealth org checks that curl is installed and each calendar's settings and files, and shows the last sync.

    Differences from org-caldav

    • A change is merged a field at a time and sent by editing the event the server has. org-caldav replaces the event with the export of the entry (dropping what org doesn't hold) and by default takes only the title and the timestamp from the calendar.
    • The description is the entry's text as written, not its ASCII export.
    • A rule a repeater can't say is written as dates, not as a diary sexp.
    • past_days defaults to 30 (org-caldav-days-in-past: everything).
    • There is no datetree inbox, no select or exclude tags, no skip conditions and no OAuth sign-in.
