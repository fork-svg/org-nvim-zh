    Command line (org)

    org-extensions-cli

    Stability: stable (org-extensions-stability)

    bin/org is a shell command that runs org.nvim in a headless Neovim (nvim --headless -l), to print the agenda, capture, clock in and out, query, change and export headings from a terminal, a status bar, cron, a launcher such as Raycast, a script or an AI agent (every command has JSON output, org-extensions-cli-json). Link it onto your $PATH:

    ln -s /path/to/org.nvim/bin/org ~/.local/bin/org

    or enable the extension and run :Org cli_install (or :Org cli_install DIR, directories complete), which asks before linking bin/org into install_dir:

    require("org").setup({ extensions = { cli = { install_dir = "~/bin" } } })

    The command itself works without the extension: enabling it only adds cli_install, the options below and a :checkhealth org section (is bin/org executable, is it the org on $PATH, which config it uses). $ORG_NVIM_BIN picks the Neovim binary (default nvim).

    With the session server on in your Neovim (remote.enabled, org-remote), every command but export, schema, version, mcp and lsp runs in that Neovim, on its buffers, its clock and its configuration, and prints the same output: a capture or org set todo edits the open buffer, and org clock in starts its clock. With none running, or with --no-server, --config, --files or --dir, org works on the files itself, as described below. -v says where a command ran.

    Configuration

    nvim -l skips your init.lua, so org loads its own configuration, the first of:

    1. --config FILE
    2. $ORG_NVIM_CONFIG
    3. stdpath("config")/org-cli.lua (~/.config/nvim/org-cli.lua)

    With none of them the defaults are used. The file is Lua: it either returns the table you pass to setup(), or calls require("org").setup() itself. Returning a table keeps it independent of your plugin manager:

    -- ~/.config/nvim/org-cli.lua
return {
  org_directory = "~/org",
  agenda_files = { "~/org/*.org" },
  capture = { templates = { t = { description = "Task",
    template = "* TODO %?\n  %U", target = "inbox.org" } } },
  clock = { persist = true },
  extensions = { cli = {}, ql = {} },
}

    Your whole init.lua works as --config too, but then every call loads all your plugins. A file that fails, returns something else than a table, or gives agenda_files or org_directory a value of the wrong type is a config error (exit 2). --files GLOB (repeatable, or comma-separated) replaces agenda_files, and --dir DIR sets org_directory.

    Nothing waits for input: prompts, confirmations and dangling-clock resolution are turned off, and a command that would need to ask (a capture template with %^{...}, say) fails with exit code 3.

    命令

    TARGET, the heading a command works on, is one of:

    id:ID or a bare IDthe heading with that ID
    FILE:LINEthe entry containing that line of FILE
    FILE::TITLEa title in FILE (home.org::*Groceries, as in a link)
    FILE::#CUSTOM_IDthe heading with that CUSTOM_ID
    title wordsa heading of the agenda files whose title contains them (ignoring case; an exact title wins), or an org-ql query when the ql extension is enabled

    FILE is an agenda file (a path, a file name or a name without .org) or any org file. When several headings match, nothing is changed: the command lists them (in JSON, details.candidates) and --pick N takes the Nth.

    Each argument is one word, except a last one of free text: TEXT, QUERY, DATE, a property VALUE, or a TARGET with nothing after it (show, id, clock in, archive) takes the remaining words. So quote a TARGET of several words that other arguments follow (set, note, refile): org set todo "Buy milk" DONE. A word no argument takes is a usage error (exit 2), never dropped. An option that takes a value is missing it when the next word is an option itself (--todo --json); give a value that looks like an option as --match=-boss.

    Reading:

    org agenda [VIEW] [--date DATE] [--span N] [--csv]The agenda as text, like org-batch-agenda. VIEW is day, week, fortnight, month, year (the date agenda with that span), todo [KEYWORD], tags MATCH, tags-todo MATCH or the key of one of your agenda.custom_commands; without it, the date agenda with your agenda.span. --date takes anything the date prompt reads (2026-10-01, +1, fri). --span takes a number of days or day, week, fortnight, month, year; anything else is a bad_value error (exit code 2). --csv is org-batch-agenda-csv.
    org search [QUERY...] [--match MATCH] [--limit N]Headings of the agenda files matching QUERY, as file:line: heading: the agenda search syntax (org-agenda-search), or org-ql queries when ql is enabled. --match takes a tags/property match (+work-boss, PRIORITY="A", org-match-syntax) instead. As in the agenda, archived and commented subtrees, and files tagged ARCHIVE in their #+FILETAGS:, are left out.
    org headlines [FILE...] [filters](also org query) Headings of the agenda files (or of the FILEs given) passing every filter: --todo KW (a keyword, or any, open for not done, done, none; repeatable), --tag TAG (own or inherited; repeatable, all must match), --property NAME=VALUE (NAME alone: has the property; inherited as use_property_inheritance says, like a property match), --level N or --level 1..2, --scheduled FROM..TO and --deadline FROM..TO (dates as --date reads them, either side optional, a single date for that day, or any, none), --file FILE (one of the agenda files), --match MATCH and --limit N. Archived and commented subtrees, and files tagged ARCHIVE in their #+FILETAGS:, are left out unless --archived. A --todo that is no keyword of the files is a bad_value error, as is a --match (here and in search) with text it can't read: where Emacs ignores the rest of a match from the first thing it can't read (+work +boss is +work), the CLI says so instead of quietly giving other headings.
    org show TARGET [--children]A heading with its properties, planning, clocks, plain timestamps and body text; --children adds the child entries (the whole subtree, each entry as the heading is shown).
    org clock [status] [--short] [--format FMT]The running clock: the one saved in clock.persist_file (with clock.persist), else the first open CLOCK line in the agenda files. --format expands %e (elapsed), %t (heading), %T (total with earlier clocks), %E (effort), %f (file) and %s (start), and prints nothing without a clock; --short uses status_format.
    org templates, org files, org tags, org keywordsThe capture templates (also org capture --list), the agenda files, the tags used in the agenda files or defined in tags, and the TODO keyword sequences with the priority range.
    org export FILE BACKEND [-o OUTPUT|--stdout]Export FILE with a back-end of :Org export (html, md, latex, pdf, ascii, ...) and print the output path, or write the text to stdout. Other formats go through pandoc (to a file only); a BACKEND that is neither is a bad_value error (exit code 2). Code blocks are evaluated as in :Org export, but one that would ask first (babel.confirm_evaluate, :eval query) stops the export with exit code 3 and nothing written, as in Emacs's batch export; babel.confirm_evaluate = false in the CLI's configuration runs them without asking (for files you trust).

    Writing (each saves the files it changed):

    org capture [-t KEY] [--field NAME=VALUE] [--input FILE] [--id] TEXT...Capture TEXT with template KEY (default: capture_template, else t, else the first). The template finishes at once, the text going where %? is (at the end without one) as if typed there: its first line continues that line and the others are indented as Org indents a new line there. After a heading they start at column 0 (at its level + 1 with adapt_indentation = true), so * %? puts the first line in the heading and the rest in its body, the heading keeping the tags that follow %?; after a list bullet they start after the bullet; else like the line of %?; in a table row each line is a row of its own. A line that would start a heading gets a space before it, as with add --body. A template that uses %i gets the text there instead, the text before %i starting each of its lines as in Emacs. TEXT - reads stdin. On Windows, org.cmd runs through cmd.exe, which cuts an argument at a newline: give text of several lines on stdin (-) or in --input. --field answers a prompt of the template by its name, the text before any |: %^{Title} and %^{Title}p by Title, %^{Size [cm]|10} by Size [cm], %^g by 标签, a date prompt by its name or Date (names ignore case). --input FILE (- for stdin) reads a JSON object { "template", "text", "fields" } instead. --id gives the new entry an ID. When the target can't be saved (a read-only file, say) the capture fails and the target, also a running Neovim's buffer of it, is left as it was: running the command again doesn't store the text twice.
    org clock in [--pick N] TARGET, org clock out, org clock cancelClock in a heading, clock out of the running clock, or cancel it.
    org add PARENT TITLE [--todo KW] [--priority P] [--tag TAG]...

    [--scheduled DATE] [--deadline DATE] [--property NAME=VALUE]...

    [--body TEXT] [--first]Add a heading TITLE as the last child of the heading PARENT (a TARGET), or with --first as its first child. A PARENT that is an org file (a path, or an agenda file's name with or without .org) adds a top-level heading at the end of that file; use FILE::TITLE or id: for a heading whose title is also a file's name. The new heading is one level below PARENT (two with odd_levels_only), after the subtree's text and before the blank lines that follow it, with a blank line before it per blank_before_new_entry.heading. KW must be a keyword of the file (a done one is set as set todo would); tags (--tag a,b or repeated), the priority, the dates (read like set scheduled), the properties and the body (split at newlines, indented per adapt_indentation) are written as org.nvim writes them. A body line starting with * at column 0 gets one space before it, so it stays text (a list item) and doesn't start a heading. A property VALUE is one line: one with a newline fails with bad_value.
    org append TARGET TEXTAppend TEXT to the body of the heading, after its planning, drawers and text and before its first child heading; TEXT - reads stdin. After text already there it starts a new paragraph (a blank line first); a lone timestamp line under the heading (the "created at" line of a capture's %U / %T) is not text, so the first append goes right under it. Lines are indented and a * line is kept as text as with add --body. On Windows, org.cmd runs through cmd.exe, which cuts an argument at a newline: give text of several lines on stdin (-). org mcp passes it whole.
    org set title TARGET TITLEReplace the title (one line), keeping the TODO keyword, priority, COMMENT and tags, like edit_headline (org-structure).
    org set todo TARGET STATE [--note TEXT]Set the TODO keyword (none or "" removes it), with org.nvim's logging, blocking and repeaters. A note the change logs gets TEXT, else it is logged without one.
    org set tags TARGET [TAGS] [--add TAG] [--remove TAG]Set the tags (a:b or a,b; "" removes them all), or add and remove some. A tag has letters and digits (of any script, café) and _ @ # %, as org-tag-re says.
    org set priority TARGET PRIORITYA, B, ... (a number with numeric #+PRIORITIES); none removes.
    org set property TARGET NAME VALUE, org set property TARGET NAME --deleteVALUE is one line (as for add --property): one with a newline fails with bad_value.

    org set scheduled TARGET DATE [--note TEXT]

    org set deadline TARGET DATE [--note TEXT]DATE as the date prompt reads it (2026-10-05 14:00, +2d, fri) or a timestamp ("<2026-10-05 Mon +1w>"); none removes the date. As when you schedule in Neovim (org-dates), the old date's repeater and warning period stay, CLOSED is removed, and the change is logged per log_reschedule / log_redeadline, with the --note text or without a note.
    org note TARGET TEXTAdd a note to the entry's log, like add_note (org-todo); TEXT - reads stdin.
    org refile TARGET DESTINATIONMove the subtree under DESTINATION, a TARGET, or to the end of an org file given by its path.
    org archive TARGETArchive the subtree with archive_default_command.
    org id TARGET [--create]The heading's ID; --create makes one when it has none.
    org protocol URL [--field NAME=VALUE]An org-protocol:// URL (org-protocol), for a URL handler: the session server handles it (a capture opens its window there). With no Neovim running, a capture is stored at once with its template, as org capture does, and store-link and open-source fail.
    org mcp [--read-only] [--isolated]Serve the commands to an AI agent as an MCP server, on stdin and stdout (org-extensions-cli-mcp).
    org lsp [--stdio]Serve the language server of the lsp extension to an editor other than Neovim, on stdin and stdout (org-extensions-cli-lsp).

    org schema [COMMAND], org help [--json], org version

    Every command writes its result to stdout and messages to stderr (-v adds org.nvim's own messages, -q hides warnings). Exit codes: 0 done, 1 failed or nothing found (search, clock out without a clock), 2 bad usage, 3 input needed, 4 the file is busy (unsaved changes in a running Neovim, another org writing) or changed on disk while the command ran.

    A write refuses a file that a running Neovim has unsaved changes in (its swap file says so), and --force writes anyway. Every file a command would write is checked before anything changes, so a refused command leaves all of them as they were (clock in checks the file of the running clock it clocks out of too). Writes go through utils.save_buffer, so the write hooks run: with crypt.encrypt_on_save the entries tagged crypt are encrypted, as when Neovim saves them (org-crypt). The hooks of all the files run before any is written; one that needs input, such as the passphrase of symmetric encryption, fails the command with exit code 3 and writes nothing, so give crypt.key (or CRYPTKEY) a public key for writes from the shell. Every write, a capture too, touches the clock stamp file, so a Neovim with the extension enabled rereads the files (see below).

    Write commands run one at a time: each holds a lock (stdpath("state")/org/cli-write.lock) while it reads and writes, so parallel calls (a script capturing in a loop, an agent's tools) wait for each other and none loses another's change. One that waits longer than lock_timeout seconds fails with file_busy (exit 4); a lock left by an org that is gone is taken over. A file another program writes while a command changes it (Neovim saving it, a sync tool) is not written over: the command fails with file_changed (exit 4) and you run it again. Without the session server only; with it, the commands run in its Neovim one after the other anyway.

    org-extensions-cli-json

    JSON

    --json makes every command print one JSON object, the envelope:

    { "version": 1, "ok": true, "command": "set todo",
  "data": { ... }, "warnings": [], "errors": [] }

    version is the version of the JSON output: it changes only when a key is removed or changes meaning (new keys can appear). command is the command's full name (clock status, set tags, ...), or null for an error found before the command is known (an unknown command or option, a flag without its value), data its result, warnings org.nvim's warnings during the command. An error makes ok false, data null and errors one object { code, message, details }, still on stdout, with the exit code of the error:

    usage (2)bad or missing arguments
    unknown_command (2)no such command
    unknown_option (2)no such option, or not one of this command
    bad_value (2)a date, keyword, priority, template, file, match or JSON that cannot be read or names nothing
    config (2)the configuration file is missing or fails
    not_found (1)no heading matches the target
    ambiguous (1)several headings match: details.candidates
    no_clock (1)no running clock
    failed (1)org.nvim refused (details.messages says why)
    internal (1)an unexpected error
    input_needed (3)the command would have to ask: details.prompt names the question (answer a capture prompt with --field; a confirmation or a passphrase can't be answered)
    file_busy (4)unsaved changes in a running Neovim: details.file, details.pid; or another org kept the write lock: details.lock
    file_changed (4)another program wrote details.file while the command changed it; it was not written, run the command again

    In JSON mode stdout holds nothing but that object and stderr stays empty unless -v, so 2>&1 is safe. A command that finds nothing exits 0 with an empty list. --jsonl prints one result per line instead (the items of agenda, the headings of search and headlines, the entries of templates, files and tags; other commands print their data on one line), and an error as the envelope line.

    The data of each command:

    agenda{ view, key, start, end, items }; an item has date, time, end_time, type (scheduled, deadline, timestamp, todo, tagsmatch, ...), todo, priority, title, tags, category, file, line, id, level, timestamp, extra, done and text (the agenda line)
    search, headlinesa list of headings
    showan entry: a heading plus properties (an object), effort_minutes, clock (count, running, minutes, total, subtree_minutes, subtree_total, entries of { start, end, minutes, line }), timestamps, body and children (entries, or null without --children)
    clock ...{ active, title, file, line, id, start, start_iso, minutes, elapsed, total, effort }; clock out and cancel: { active, title, file, minutes, duration, canceled }
    capture{ file, line, template, type, id, headline }
    add{ headline, parent } (parent null for a heading added at the top level of a file)
    append{ headline, text }
    set ..., note{ headline, field, old, new } (and repeated for set todo, name for set property)
    refile{ headline, from: { file, line } }
    archive{ title, from, archive_file, headline }
    id{ id, created, headline }
    templatesa list of { key, description, type, target, group }
    filesa list of { file, title, category, headlines }
    tagsa list of { name, count, defined }
    keywords{ sequences, todo, done, priority }
    export{ file, backend, output, text }

    A heading is { file, line, end_line, level, id, custom_id, todo, todo_type ("todo", "done" or null), priority, title, raw_title, tags (with inherited ones), local_tags, category, outline_path, scheduled, deadline, closed, archived, commented }. A timestamp is { raw, date, time, end_time, start, end, active, repeater, warning }, where raw is the org text (<2026-10-02 Fri 10:00-11:00 +1w>) and start and end are ISO 8601 in local time (2026-10-02T10:00, 2026-10-02 without a time). Paths are absolute; a missing value is null.

    org schema prints all of this as JSON: every command with its usage, arguments, flags, an input_schema (a JSON Schema of its arguments and flags) and the JSON Schema of its data, the error and exit codes, and the shared types under $defs. org schema set todo describes one command; org help --json (or org COMMAND --help --json) is the same in an envelope.

    示例

    The running clock in the tmux status line (refreshed every 15 seconds):

    set -g status-interval 15
set -g status-right "#(org clock status --format '#[fg=green]%e %t')"

    Today's agenda mailed every morning, and the week written to a file every hour, with cron:

    0 7 * * *  org agenda day | mail -s "Agenda" me@example.com
0 * * * *  org agenda week > ~/public/agenda.txt

    Next three timed items for a status bar (SketchyBar, waybar, ...):

    org agenda --jsonl | jq -r 'select(.time) | "\(.time) \(.title)"' | head -3

    More jq one-liners:

    # overdue deadlines, oldest first
org headlines --todo open --deadline ..yesterday --json |
  jq -r '.data | sort_by(.deadline.start)[] | "\(.deadline.date) \(.title)"'
# minutes clocked on a task
org show id:4f1c... --json | jq '.data.clock.subtree_minutes'
# mark the first NEXT of a project done, by its ID
id=$(org headlines --todo NEXT --file projects --limit 1 --json | jq -r '.data[0].id')
org set todo "id:$id" DONE
# what failed, and why
org set todo "Write report" DONE --json | jq -r '.errors[] | "\(.code): \(.message)"'

    Capture from a launcher or a shell alias, or with the answers of a template's prompts:

    org capture -t t "Call the dentist"
pbpaste | org capture -t n -
org capture -t m --field Who=Ann --field When=fri "Talk about the offsite"
echo '{"template":"t","text":"Renew passport"}' | org capture --input - --json

    An agent tool

    The CLI makes a small tool interface for an AI agent: the agent runs org ... --json, reads ok, data and errors, and retries an ambiguous target with --pick N or an ID. org schema gives the input_schema of every command, ready to pass as a tool definition, for example to the Anthropic API:

    {
  "name": "org_set_todo",
  "description": "Set the TODO keyword of an org heading (org set todo).",
  "input_schema": {
    "type": "object",
    "properties": {
      "target": { "type": "string", "description": "id:ID, FILE:LINE, FILE::TITLE or title words" },
      "state": { "type": "string", "description": "a TODO keyword, or none" },
      "note": { "type": "string", "description": "--note: text of a log note" }
    },
    "required": ["target", "state"]
  }
}

    The tool's handler runs org set todo TARGET STATE [--note NOTE] --json (the arguments as separate words, not through a shell) and returns the envelope. To generate one tool per command:

    org schema | jq '[.commands[]
  | select(.name != "help" and .name != "mcp") | {
  name: ("org_" + (.name | gsub(" "; "_"))),
  description: .summary, input_schema: .input_schema }]'

    A read-only agent gets the commands whose writes is false. An agent that speaks MCP needs none of this: org mcp serves the same tools.

    org-extensions-cli-mcp

    MCP server

    org mcp is a Model Context Protocol server for AI agents and the apps that run them (Claude Code, Claude Desktop, editors with an MCP client): it reads JSON-RPC 2.0 messages from stdin, one per line, and writes its answers to stdout, until stdin closes. Add it to a client as a stdio server whose command is org mcp. For Claude Code:

    claude mcp add org -- org mcp

    or, in a project's .mcp.json (Claude Desktop's claude_desktop_config.json takes the same mcpServers object):

    { "mcpServers": { "org": { "command": "org", "args": ["mcp"] } } }

    A desktop app may not see your shell's $PATH: give command the full path of bin/org then. Global options go before mcp and apply to every tool call ("args": ["--config", "/path/cfg.lua", "mcp"]).

    Every command but schema, help, version, protocol, mcp and lsp is a tool, named after it with _ for spaces (agenda, headlines, show, capture, clock_in, set_todo, note, refile, export, ...), with a description written for the agent: what the tool is for and when to use it. The server's instructions tell the agent how targets, dates and errors work, and today's date. A tool's input schema is the command's input_schema from org schema, without --force (a file with unsaved changes in Neovim gives file_busy, so the agent asks you to save it), --input, --list and --csv. Arguments the tool doesn't take, or a missing one, are an error result the agent can correct. Text arguments can't be "-": the server's stdin is the protocol. Each tool is annotated as read-only or not (readOnlyHint), and as replacing what is there (destructiveHint: set_*, refile, archive, clock_cancel, export) or not.

    A tool's result is the command's data (org-extensions-cli-json) as JSON text, made shorter for the agent to read: null fields, empty lists and false flags are left out, a timestamp is its Org text and its ISO start and end, paths under your home directory start with ~/, and every heading has a target (id:ID, or FILE:LINE) that a tool taking a heading reads back. A failed call is a result with isError set and the text { error, message, details }, error being the error code. search and headlines return at most 50 headings when the call gives no limit, and say so when more match. Warnings come as a second text.

    Prompts

    The server also offers prompts, which a client shows as commands (in Claude Code /mcp__org__plan_day):

    plan_daytoday's agenda, deadlines and open tasks, and a plan for the day
    weekly_reviewa weekly review: what got done, what is coming, stale tasks, the inbox
    triage_inboxa proposed action for each captured item (file: the inbox, by default where the templates capture)

    Each asks the agent to propose changes and make them once you agree.

    Each call runs org COMMAND ... --json as from a shell: it sees the files as they are on disk and writes them as org does (the swap-file guard, the write hooks); with the session server on (org-remote) the call runs in that Neovim instead, unless --config, --files, --dir or --no-server came before mcp. Otherwise the server runs it in its own Neovim, which loaded the configuration when it started (restart the server after changing it), and then closes what the call opened: the next call reads the files, the running clock and the ID database again, so it sees what Neovim or another org changed meanwhile. A call takes a few milliseconds, the agenda of many files longer. export, which runs code blocks and other programs, runs in a new Neovim. With --isolated (or the mcp.isolated option) every call does: each then takes as long as org from a shell, the configuration is read each time, and a call still running after 10 minutes is stopped, where one that hangs in the server's Neovim holds up the calls after it. Calls are answered in order, one at a time. Nothing but protocol messages goes to stdout; -v copies each call's messages to stderr, which clients log.

    --read-only (or the mcp.read_only option) leaves out the tools that change files (every writes command, and export, which writes its output file); calling one anyway gives an error result. The server speaks MCP protocol versions 2025-06-18, 2025-03-26 and 2024-11-05.

    org-extensions-cli-lsp

    Language server for other editors

    org lsp (--stdio is accepted and changes nothing: it is the only transport) runs the language server of org-extensions-lsp as a program, for editors that start one: Helix, VS Code, Zed, Emacs, Kakoune. It speaks LSP on stdin and stdout (Content-Length headers) until the editor sends exit or closes stdin, and exits 0 after a shutdown, 1 without one. Messages go to stderr, which editors log. It takes no --json or --jsonl (the protocol is already JSON), and it doesn't run in a session (org-remote): it always starts its own Neovim.

    It reads the configuration as every org command does (--config, $ORG_NVIM_CONFIG or stdpath("config")/org-cli.lua): org_directory, agenda_files, TODO keywords, and the extensions.lsp options if you enable it there. The editor's workspace folders join the workspace files (references, rename, workspace symbols). A document the editor opens is read from what the editor sends, unsaved changes included; other files from disk.

    Everything the server does in Neovim works, with these differences:

    • no code lenses, and the code actions are only those that are edits (lint quick fixes, conversions): the commands (TODO state, schedule, refile, ...) run org actions in a Neovim buffer, which the editor wouldn't see;
    • a rename's edits are applied by the editor, in open and closed files alike (rename.write_unloaded doesn't apply);
    • positions are UTF-8 when the editor offers it (Helix, Neovim), else UTF-16, which every editor takes.

    Helix (~/.config/helix/languages.toml):

    [language-server.org]
command = "org"
args = ["lsp", "--stdio"]

[[language]]
name = "org"
scope = "source.org"
file-types = ["org"]
roots = []
comment-token = "#"
language-servers = ["org"]

    Emacs (eglot):

    (with-eval-after-load 'eglot
  (add-to-list 'eglot-server-programs
               '(org-mode . ("org" "lsp" "--stdio"))))

    then M-x eglot in an Org buffer. VS Code and Zed start language servers through extensions: use a generic LSP client extension, with the command org, the arguments lsp --stdio and the org language. Give the full path of bin/org when the editor doesn't see your shell's $PATH, and global options before lsp (["--config", "/path/cfg.lua", "lsp", "--stdio"]).

    Each org lsp is its own Neovim (nvim --headless): it answers initialize within about 0.1 s of starting, then parses the workspace in the background as in Neovim.

    Options (extensions.cli)

    install_dirwhere cli_install links org ("~/.local/bin")
    capture_templatetemplate key of org capture without -t (nil)
    status_formatformat of org clock status --short ("%e %t")
    watch_clocka running Neovim follows the shell's clock (true)
    lock_timeoutseconds a write waits for another org writing before it fails with file_busy (10)
    mcp.read_onlyorg mcp lists only the tools that don't change files, as --read-only (false)
    mcp.isolatedorg mcp runs each tool call in a new Neovim, as --isolated (false)

    Clock in the shell and in Neovim

    Every write (org clock in, out and cancel, capture, set, ...) touches stdpath("data")/org/cli-clock.stamp. A Neovim with the extension enabled (and watch_clock) checks that file every two seconds and on FocusGained; when it changed, Neovim rereads changed files (:checktime), drops its running clock when the open CLOCK line is gone, or takes up an open CLOCK line of the agenda files, and says so. org clock status sees a clock started in Neovim, from clock.persist_file or the saved CLOCK line.

    Limits

    • Each call starts Neovim and parses the agenda files: about 0.25 s for 200 files of 25 entries each (the agenda itself is most of it, so a parse cache would gain little), fine for a status bar every few seconds, not for a tight loop. org mcp starts Neovim once, and parses again only the files that changed.
    • The CLI edits files on disk. A Neovim that has the same file open sees the change as a file changed outside it ('autoread'), at once with the extension enabled (it watches the stamp file). The CLI does not write a file with unsaved changes in a running Neovim (exit 4), but finds those only through the swap file in the default 'directory'; with swap files off, or on Windows, a Neovim buffer with unsaved changes asks as usual.
